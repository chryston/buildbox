# Legacy fixtures

Golden inputs for the migration and floor-plan suites — S1 (migration correctness),
S2 (migration performance) and S4 (floor-plan render performance) in
`docs/adr/0008-testing-and-licence-strategy.md`. Later issues cite these paths, so the
layout is fixed.

**Fixtures are never deleted or regenerated.** A fixture is a record of what a past
build persisted; regenerating one from a newer build silently rewrites the thing S1 and
S2 compare against. A new schema version gets a new file.

`src/test/legacyFixtures.test.ts` checks that every file here still matches the SHA-256
in the [Integrity](#integrity) table and that each `buildbox-store.json` is still a
persist envelope at its recorded version. Change one byte and that test fails.

## How the captured fixtures were made

Each `buildbox-store.json` is the **exact raw string** that version of the app wrote to
`localStorage['buildbox-store']` — not reformatted, not hand-edited.

1. Check out the source commit in a throwaway worktree, `npm ci && npm run build`,
   serve it with `vite preview` (the app is served under the `/buildbox/` base path).
2. Seed a hand-authored state into `localStorage` with `page.addInitScript` and load the
   page, so the app rehydrates from it.
3. Dispatch a click on a void so the app's own zustand-persist write fires, then read the
   raw value back out of `localStorage` and write it to the fixture file.

In every capture the value the app wrote was byte-identical to the value it was given,
which is what makes these files trustworthy as "what this build persists". No capture
produced a `pageerror` or a `console.error`. The capture driver was throwaway and is not
committed.

The state behind all five store fixtures is the same cabinet content, expressed in the
shape that version used: 2–3 projects, a tree of depth 4 splitting on both axes, a pinned
node (`locked: true`, `fixedSize: 180`), `spaceLabel` on voids, `drawer` in both side and
undermount mount modes, `hanging-space`, `microwave`, divider groups (walnut and birch),
`door` and `drawer-front` accessories (the door with a `pull`), toe-kick
`{height: 100, setback: 50}` (null on the inch unit), and settings in `mm`, `cm` and `in`.

### Two commits differ from the issue text

Both substitutions are recorded here because the issue's commits cannot produce the
fixture the issue asks for.

- **v0 comes from `cb1f673`, not `954b673^` (`fcc0440`).** `fcc0440` builds and still
  persists version 0, but it crashes on load — `computeCutList(design)` reads
  `design.units` while the store still holds `{root, globalSettings}`, so the app dies
  with `Cannot read properties of undefined (reading 'flatMap')` even with empty storage.
  `cb1f673` is the last commit that persists the v0 shape *and* runs.
- **v1 comes from `76158b3`, not `1f8a45a^` (`7acecd3`).** `7acecd3` is after the
  `defaultMaterial` → `material` rename (`e582171`), so a fixture captured there cannot
  contain `defaultMaterial` (pre-rename), which is the point of the v1 fixture.
  `76158b3` still persists `version: 1` *and* `defaultMaterial`.

v2 comes from `411fedd` and v3 from `8071580` (main at capture time), as specified.

## Noise images

The floor-plan images are deterministic noise, generated by `scripts/make-noise-png.mjs`
(mulberry32 PRNG, fixed seed, `zlib` level 6 — byte-identical on every run and every
platform, unlike `canvas.toDataURL()`). Noise is used because it does not compress, which
is what makes the large fixture a real localStorage and render-cost test.

```sh
node scripts/make-noise-png.mjs --width 256  --height 192  --seed 20260529   # v3
node scripts/make-noise-png.mjs --width 1200 --height 1000 --seed 20260529   # v3-large-image
```

| Image | Decoded PNG bytes | PNG SHA-256 | Base64 data URL chars |
| --- | --- | --- | --- |
| 256×192 (`v3`) | 147,761 | `2bf8cc1f75e2a76ff78947bf2cfe9e463305915f6f4ee2945df84285aa4ece69` | 197,038 |
| 1200×1000 (`v3-large-image`) | 3,602,163 | `8dc0df5ac11b522c70ae3e9614da477fe23cbee03033d0b174066817d027f586` | 4,802,906 |

`v3-large-image` is the localStorage ceiling case. Measured in this Chromium build
(headless shell, fresh origin, single key): a 4.8 M-char value stores, a 5.0 M-char value
throws `QuotaExceededError`. The whole envelope is 4,809,118 chars and stores and
rehydrates cleanly — the fixture sits just under the ~10 MB UTF-16 per-origin limit, which
is the point. Its plan is deliberately **uncalibrated** (`pixelsPerMm: null`), so S4
cannot inherit the small fixture's calibration.

## Files

### `v0/buildbox-store.json` — captured, `cb1f673`

Envelope `{state: {projects, activeProjectId}, version: 0}`. 3 projects — *Kitchen Base*,
*Kitchen Tall*, *Bathroom Vanity* — each a bare `Design` (`{id, name, root, globalSettings}`)
with one root. 27 nodes. Settings carry `defaultMaterial` (walnut / white / oak) and units

Two keys in this file are read by today's app but ignored by the build that wrote them:
`spaceLabel`, and node-level `material` on one void. They survive the persist round-trip
verbatim, which is exactly the situation S1 has to handle.

### `workspace/v0-design-shape.buildbox.json` — hand-authored

A `WorkspaceFile` whose single project is still in the pre-`units` `Design` shape
(`{id, name, root, globalSettings}` with `defaultMaterial`), which is what
`readLegacyWorkspaceFile` → `upgradeLegacyDesign` has to accept. The workspace export path
never produced this shape — it postdates the units migration — so it is written by hand
rather than captured. *Legacy Closet*: depth-3 tree on both axes, a hanging space, a
3-drawer bank, one pinned node, mm settings.

#40 corrected the node fields to the vocabulary the app has always written
(`splitAxis: horizontal|vertical`, `drawerConfig: {slideType, reveal}`). The first
hand-authored copy invented `splitAxis: "x"/"y"` and `drawerConfig: {count, mount}`, which
no BuildBox version ever wrote and the engine cannot read; the frozen legacy reader rejects
them, so the fixture was wrong rather than the rule. The hash below is the corrected file.

### `floor-plan/no-image-floor-plan.json` — captured, `8071580`

## Edge cases (#43)

Hand-authored, one converter edge each. They live in their own directory rather than in
`workspace/` because that one is asserted *clean* — `src/test/legacyFixtures.test.ts`
requires every `workspace/*.buildbox.json` to pass the frozen reader — and the duplicate-ID
file below does not: the reader stops at the repeated unit ID, which is exactly the input
#43 has to repair rather than refuse.

### `edge-cases/floor-plan-sketches.json` — hand-authored

A floor-plan export with no image, no calibration, one custom object, one custom template
and nothing else but five wall-hack / tile-zone annotations. It is the plan whose entire
annotation layer goes nowhere in domain v1 (#20 §3), so it is what #43 checks the
"discarded" count against: the object and the template survive, the annotations are
reported and dropped.

### `edge-cases/workspace-duplicate-node-id.buildbox.json` — hand-authored

Two projects that each reuse one ID inside themselves: `proj-dup-space` has two sibling
nodes both called `space-shared`, and `proj-dup-unit` has two units both called `unit-twin`
(the active project, so it is the one the review opens first). Domain v1 keeps one ID
namespace per Project, so neither can be copied across as it stands — this is the input the
ID-regeneration report is for.

### `edge-cases/workspace-unknown-setting-field.buildbox.json` — hand-authored

Two otherwise identical cabinets where the second carries `"colour": "#f4f1ea"` in its
`settings` — a field no BuildBox version has ever written and nothing reads. The legacy
reader says nothing about it (it ignores what it does not model); domain v1 rejects it. The
pair shows both halves of #43: the good project converts, the bad one is rejected with a
problem that names the field and where it sits.
